# Compliance Rule Manager

An internal web app so IT staff can create Google Workspace compliance rules without hunting through the
Admin console menus: sign in with a Google Workspace admin account, and generate

1. a **Gmail rule** blocking mail from a specific address, to a specific address, or between two specific
   addresses - internal or external, in any combination Google Workspace can actually see, and/or
2. a **Drive trust rule** blocking Drive sharing from one specific person to another specific person, via a
   guided Google Group + trust rule workaround.

## Read this first: what's actually automated

Before relying on this tool, it's worth knowing exactly what Google allows any outside app to do, because
it's more limited than the Admin console UI itself:

- **Classic Gmail "Content compliance" rules** (Apps &rarr; Gmail &rarr; Compliance in the Admin console) and
  **Drive "Trust rules"** (Security &rarr; Rules &rarr; Trust) have **no write API** - Google's own settings
  reference marks both as read-only. No app, including this one, can create them without a human clicking
  through the console.
- Google's newer **Cloud Identity Policy API** gained real create/update/delete support for **DLP (Data Loss
  Prevention) rules** in June 2026 - a different, newer feature that achieves the same practical outcome as a
  content-compliance block (stop mail matching a condition on a given route, scoped to an OU), via a different
  underlying Google feature (Security &rarr; Data protection rather than Gmail &rarr; Compliance). This
  includes a real block action (`gmailAction.blockContent`) - confirmed on 2026-08-14 by reading back a real
  rule from this district's own tenant, after an earlier draft of this doc wrongly concluded (from one Admin
  console screenshot that happened to be missing the option) that blocking wasn't available here at all.
- There is still no API of any kind - read or write - for Drive trust rules, from Google or anyone else, as of
  when this app was built. Confirmed by checking the Cloud Identity Policy API's full list of supported settings
  types: it doesn't mention trust rules even as a read-only entry, unlike DLP rules which are fully read/write.
  So this app can help you *prepare* a trust rule, but it can never list, verify, or delete one for you - manage
  existing trust rules directly in Admin console &rarr; Rules.
- Drive trust rules also have an asymmetry worth knowing: a rule's **Scope** (the sender/owner side) can only be
  an org unit or a group, never a single named individual - but its **Condition** (the target side) *can* name
  one specific person. So blocking sharing from one specific person to another requires a workaround: put the
  sender alone in a throwaway Google Group, then write the trust rule against that group with the recipient
  named in the condition. This app's Drive wizard walks you through exactly that, including the reverse
  direction if you want it blocked both ways.

**What this means in the app right now:** the Drive trust rule always goes through the guided manual/deep-link
flow (no API exists for it at all, in either direction). The Gmail rule defaults to the same guided manual flow, but can optionally
create the rule live via the `ENABLE_LIVE_DLP_API` flag (`server/.env`) - the app fills in every value and
calls Google directly, falling back automatically to the manual flow if the live call fails for any reason.
Every field in the request (org unit, block action, address-matching condition, and the required rule metadata)
was confirmed against this district's real tenant on 2026-08-14 - not guessed - by creating and reading back
real test rules through OAuth Playground. The wizard takes a sender address, a recipient address, or both
(leave one blank to mean "anyone") and turns that into a genuine `all_headers.contains('the-address')` content
condition - this API is a *Data Loss Prevention* API at heart and rejects a tautological/empty match condition
outright, so real address matching turns out to be exactly what it wants, not a workaround. Blocking everything
*to* one internal address needs two separate Google rules under the hood (mail can arrive from an internal
sender or an external one, and Gmail DLP triggers only cover one direction each) - the app creates both and
rolls back automatically if only one succeeds, so you never end up with a half-applied block. Also confirmed:
this API has no duplicate protection - an identical request sent twice creates two separate active rules, not
an error. See the comment at the top of `server/src/services/policyService.ts` for the full confirmed schema.
Recommend testing the flag against a low-stakes address pair before turning it on for real.

A note on **GAM** (the popular open-source Workspace admin CLI): its changelog claims DLP create/update/delete
support was added around the same time as Google's API update, but GAM's own command reference still only
documents read commands (`gam show/print/info policies`) as of this writing. If you use GAM elsewhere in your
workflows, double check its actual command support yourself (`gam version`, `gam help create policy`) rather
than assuming the changelog entry is fully live - this app doesn't depend on GAM at all, it talks to Google's
API directly.

## How admin access is checked

There's no simple Google API to check "does this admin specifically have Gmail/Security privileges." Instead:
the Admin SDK Directory API can only be called successfully by an account with *some* admin role in the first
place (a regular user's call fails with 403). So this app treats "the Directory API call succeeds" as proof of
admin access, and additionally reports whether the account is a super admin or a delegated admin. If a
delegated admin without the specific privilege needed for a given rule tries to create one, Google's own API
will reject the call and the app surfaces that error - it doesn't pretend to succeed.

## One-time Google Cloud setup

You need a Google Cloud project associated with your Workspace domain to get OAuth credentials.

1. Go to [console.cloud.google.com](https://console.cloud.google.com) and create a new project (or reuse an
   existing internal-tools project).
2. **Enable APIs**: APIs & Services &rarr; Library &rarr; enable:
   - **Admin SDK API**
   - **Cloud Identity API**
3. **Configure the OAuth consent screen**: APIs & Services &rarr; OAuth consent screen.
   - User type: **Internal** (restricts sign-in to your Workspace domain automatically - pick this if your
     Cloud project is associated with your Workspace org).
   - Add the scopes listed in `server/src/config.ts` (`OAUTH_SCOPES`).
4. **Create an OAuth client**: APIs & Services &rarr; Credentials &rarr; Create Credentials &rarr; OAuth
   client ID &rarr; Web application.
   - Authorized redirect URI: `http://localhost:3000/auth/google/callback` for local testing, and/or
     `https://<your-real-hostname>/auth/google/callback` (no port, **must be `https://`**) for the deployed
     server. You can list both at once. Google only allows plain `http://` for `localhost`/`127.0.0.1` - every
     other hostname is rejected outright unless it's `https://`. See "Troubleshooting" in
     [SETUP.md](./SETUP.md) if you hit `redirect_uri_mismatch`.
   - Copy the generated **Client ID** and **Client secret** into `server/.env` (`GOOGLE_CLIENT_ID`,
     `GOOGLE_CLIENT_SECRET`).
5. The signed-in user needs an actual Workspace admin role (super admin, or a delegated role with at least
   Organizational Units + Security/Groups read privileges) to use the app at all - see "How admin access is
   checked" above.

  src/auth/         OAuth flow, session handling, admin-role check

  src/routes/       HTTP routes
client/            React + TypeScript frontend (Vite)

## Local development

```bash
npm install --workspaces
cp server/.env.example server/.env   # then fill in the values
npm run dev:server                    # terminal 1
npm run dev:client                    # terminal 2
```

Open http://localhost:5173.

## Security notes

- OAuth access/refresh tokens are stored server-side in the session only, never sent to the browser.
- The signed-in user's own Google credentials are used for every Google API call the app makes - the app
  itself holds no standing service-account access to your Workspace data, so it can only ever do what that
  specific admin is already allowed to do.
- Every rule created or prepared is written to a local audit log (`server/data/audit-log.json`) with who
  requested it and when.
