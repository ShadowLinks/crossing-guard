An internal web app so IT staff can create Google Workspace compliance rules without hunting through the
Admin console menus: sign in with a Google Workspace admin account, pick an org unit, and generate

1. a **Gmail rule** blocking mail internal&rarr;internal, internal&rarr;external, or external&rarr;internal, and/or
2. a **Drive trust rule** blocking (or limiting) sharing files outside your organization,

both scoped to a specific OU.

## Read this first: what's actually automated

Before relying on this tool, it's worth knowing exactly what Google allows any outside app to do, because
it's more limited than the Admin console UI itself:

- **Classic Gmail "Content compliance" rules** (Apps &rarr; Gmail &rarr; Compliance in the Admin console) and
  **Drive "Trust rules"** (Security &rarr; Rules &rarr; Trust) have **no write API** - Google's own settings
  reference marks both as read-only. No app, including this one, can create them without a human clicking
  through the console.
- Google's newer **Cloud Identity Policy API** gained real create/update/delete support for **DLP (Data Loss
  Prevention) rules** in June 2026 - a different, newer feature that could in principle achieve the same
  practical outcome as a content-compliance block (stop mail matching a condition on a given route, scoped to
  an OU), just via a different underlying Google feature (Security &rarr; Data protection rather than Gmail
  &rarr; Compliance).
- There is still no write API of any kind for Drive trust rules, from Google or anyone else, as of when this
  app was built.

**What this means in the app right now:** both rule types always go through the guided manual/deep-link flow -
the app fills in every value and hands you a direct link into the Admin console to finish with a couple of
clicks. The `ENABLE_LIVE_DLP_API` flag exists for the Gmail path but currently does **not** create anything
live: testing against a real tenant turned up Google's exact request schema for the parts that scope and name
a DLP rule (confirmed working), but there's no published schema for the part that would filter by
sender/recipient domain (internal vs. external) or actually block a Gmail message. Guessing that part isn't
like guessing a field name - a wrong guess there could be silently *accepted* by Google while creating a rule
broader than intended (e.g. blocking all mail from an OU instead of just mail to external addresses), which is
worse than the call simply failing. So `createLiveGmailDlpRule()` deliberately throws before sending anything,
explaining exactly what's missing. See the large comment at the top of `server/src/services/policyService.ts`
for the full confirmed-vs-unconfirmed breakdown and how to capture the missing piece (via the Admin console's
own network requests) if you want to finish wiring this up.

A note on **GAM** (the popular open-source Workspace admin CLI): its changelog claims DLP create/update/delete
support was added around the same time as Google's API update, but GAM's own command reference still only
documents read commands (`gam show/print/info policies`) as of this writing. If you use GAM elsewhere in your
workflows, double check its actual command support yourself (`gam version`, `gam help create policy`) rather
than assuming the changelog entry is fully live - this app doesn't depend on GAM at all, it talks to Google's
API directly.

## How admin access is checked

There's no simple Google API to check "does this admin specifically have Gmail/Security privileges." Instead:
the Admin SDK Directory API can only be called successfully by an account with *some* admin role in the first
place (a regular user's call fails with 403). So this app treats "the Directory API call succeeds" as proof of
admin access, and additionally reports whether the account is a super admin or a delegated admin. If a
delegated admin without the specific privilege needed for a given rule tries to create one, Google's own API
will reject the call and the app surfaces that error - it doesn't pretend to succeed.

## One-time Google Cloud setup

You need a Google Cloud project associated with your Workspace domain to get OAuth credentials.

1. Go to [console.cloud.google.com](https://console.cloud.google.com) and create a new project (or reuse an
   existing internal-tools project).
2. **Enable APIs**: APIs & Services &rarr; Library &rarr; enable:
   - **Admin SDK API**
   - **Cloud Identity API**
3. **Configure the OAuth consent screen**: APIs & Services &rarr; OAuth consent screen.
   - User type: **Internal** (restricts sign-in to your Workspace domain automatically - pick this if your
     Cloud project is associated with your Workspace org).
   - Add the scopes listed in `server/src/config.ts` (`OAUTH_SCOPES`).
4. **Create an OAuth client**: APIs & Services &rarr; Credentials &rarr; Create Credentials &rarr; OAuth
   client ID &rarr; Web application.
   - Authorized redirect URI: `http://localhost:3000/auth/google/callback` for local testing, and/or
     `https://<your-real-hostname>/auth/google/callback` (no port, **must be `https://`**) for the deployed
     server. You can list both at once. Google only allows plain `http://` for `localhost`/`127.0.0.1` - every
     other hostname is rejected outright unless it's `https://`. See "Troubleshooting" in
     [SETUP.md](./SETUP.md) if you hit `redirect_uri_mismatch`.
   - Copy the generated **Client ID** and **Client secret** into `server/.env` (`GOOGLE_CLIENT_ID`,
     `GOOGLE_CLIENT_SECRET`).
5. The signed-in user needs an actual Workspace admin role (super admin, or a delegated role with at least
   Organizational Units + Security/Groups read privileges) to use the app at all - see "How admin access is
   checked" above.

```bash
npm run dev:server                    # terminal 1
npm run dev:client                    # terminal 2
```

Open http://localhost:5173.

## Security notes

- OAuth access/refresh tokens are stored server-side in the session only, never sent to the browser.
- The signed-in user's own Google credentials are used for every Google API call the app makes - the app
  itself holds no standing service-account access to your Workspace data, so it can only ever do what that
  specific admin is already allowed to do.
- Every rule created or prepared is written to a local audit log (`server/data/audit-log.json`) with who
  requested it and when.
